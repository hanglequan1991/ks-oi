# TC-18: Every page and response carries a noindex instruction

- id: TC-18
- story: [STORY-16](../stories/STORY-16.md)
- verifies: AC9
- status: blocked (not reworked in Version 1; see board)
- rework count: 0
- automation test file: `sheet-rag/e2e/TC-18.e2e.ts`
- runs without Cloudflare credentials: yes (HTTP requests plus one browser check)

## Preconditions
- TASK-9, TASK-11 and TASK-14 done; Playwright installed.
- Harness (inline in the test file, no shared helper): a Node `http` server on port 0 that converts each request to a `Request`, calls `createApp(deps).fetch`, and also serves `sheet-rag/public/lang.js` and `app.css` as static files (stands in for the Workers assets binding). `deps.getSettings` is a fake returning sample `SiteSettings` with distinct sample texts. `mount` registers sample routes using `Layout` and `renderPage`. Mounted routes: `/sample`, `/priced`, `/api/hotels` (JSON), plus an unknown path for 404. Both `/` and `/en/` variants are requested.

## Steps
1. Request `/sample`, `/en/sample`, `/priced`, `/en/priced`.
2. Request the JSON route `/api/hotels` and an unknown path `/nope`.
3. Send requests to `/api/hotels` with the header `CF-Connecting-IP: 203.0.113.9` until the data limit is exceeded (read the limit from `RATE_LIMITS.data`; see TC-20), and read the headers of the 429 response.
4. In the browser open `/sample` and read `meta[name=robots]`.

## Expected results
1. Every HTML response has header `X-Robots-Tag: noindex, nofollow` and `<meta name="robots" content="noindex, nofollow">` in the body.
2. The JSON response and the 404 response have `X-Robots-Tag: noindex, nofollow`.
3. The 429 response also has `X-Robots-Tag: noindex, nofollow`.
4. The browser DOM contains the robots meta with value `noindex, nofollow`.
5. No page contains a link to `/bill` or to an admin path (billing page not linked anywhere).

## Test data
- Paths above; one client IP `203.0.113.9`, sent as `CF-Connecting-IP`, for the 429.

## Review
Verdict: rework

I ran `npx playwright test -c playwright.node.config.ts e2e/TC-18.e2e.ts --trace off --project=chromium`: 4 passed. Steps 1, 2 and 4 follow the TC and assert real things (header and meta on all four HTML pages, exactly one robots meta, no /bill or /admin links, JSON and 404 header, DOM meta in the browser). No sleeps; the limit is read from `RATE_LIMITS.data`. The test only touches its own file.

Finding on the 429 header: `defaultClientKey` in `src/web/middleware/rateLimit.ts` uses `CF-Connecting-IP` first, then the first `X-Forwarded-For` entry, then `"unknown"`. `app.ts` does not pass a custom `clientKey`, so this default applies to every limiter. The test's `X-Forwarded-For` therefore does key the limiter (it is not ignored and requests do not share one key), because no `CF-Connecting-IP` is sent. It passes, but only through the fallback path. The TC text said X-Forwarded-For, which was my wording error; the design, TC-20 and the other TCs use `CF-Connecting-IP`. I amended step 3 and the test data above.

Bypass risk: in production on Cloudflare, the edge always sets `CF-Connecting-IP` (a client-sent value is overwritten), so `X-Forwarded-For` is never read and cannot be used to dodge the limit. The fallback is only reachable when the header is missing (local node harness, direct non-Cloudflare access), where a spoofed `X-Forwarded-For` would let a client rotate keys. Low risk, and the fallback is specified (TASK-12 AC10, TC-20 step 6), so it is not a defect. Lead may want to confirm the Worker is never reachable without Cloudflare in front.

Rework notes for qa:
1. In step 3 (`RATE_LIMITED_IP` header, lines 7-8 and 201 of `e2e/TC-18.e2e.ts`), send `CF-Connecting-IP: 203.0.113.9` instead of `X-Forwarded-For`, and update the header comments to match. Keep the rest unchanged. The fallback is TC-20's job.
2. Update the QA notes in this file: step 3 now reads as in the amended TC, so the "Step 3 wording" note is no longer needed.
