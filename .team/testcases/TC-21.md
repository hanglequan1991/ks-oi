# TC-21: A rate-limited client is accepted again when the waiting period ends

- id: TC-21
- story: [STORY-16](../stories/STORY-16.md)
- verifies: AC11, AC10
- status: todo
- rework count: 0
- automation test file: `sheet-rag/e2e/TC-21.e2e.ts`
- runs without Cloudflare credentials: yes (injected memory limiters with a fake clock)

## Preconditions
- TASK-12 and TASK-14 done; Playwright installed (plain Node test).
- Harness (inline in the test file, no shared helper): a Node `http` server on port 0 that converts each request to a `Request` and calls `createApp(deps).fetch`. `mount` registers stub handlers for `/search`, `/chat`, `/api/suggest`, `/api/hotels` that increment a counter (they stand in for the AI service and the data layer). `createApp` receives `limiters` built with `createMemoryLimiter({ limit: 3, windowMs: 60000, now })` where `now` returns a variable the test controls (no real waiting, no sleeps).

## Steps
1. Send 3 requests to `/search?q=a` from one IP; send a 4th.
2. Advance the fake clock by 59,999 ms; send another request.
3. Advance the fake clock to exactly `windowMs` after the window start; send another request.
4. Send 3 more requests, then a 5th overall in the new window.
5. Check the other limiter groups (chat, suggest, data) were not consumed by the search requests.
6. Failure case: pass `limiters` whose `limit` throws, and then no limiters for a group.

## Expected results
1. Requests 1 to 3 return 200, the 4th returns 429 with `Retry-After`.
2. Still 429 just before the window ends.
3. The request is accepted with 200.
4. The new window allows its quota (3 requests total in the window) and refuses the one after it: counting restarts instead of staying blocked.
5. Other groups still have their full quota.
6. A throwing or missing limiter lets requests through (fail open: HTTP 200, a `console.warn` is logged), so a limiter outage never takes the site down.

## Test data
- Limit 3, window 60,000 ms, fake clock start 1,000,000.
