# TC-24: LIVE - the real Cloudflare rate limiter refuses abusive clients and recovers

- status: todo

- automation test file: `sheet-rag/e2e/TC-24.e2e.ts`
- runs without Cloudflare credentials: no (needs the deployed Worker with Workers Rate Limiting bindings; skipped when `LIVE_BASE_URL` is not set)

## Preconditions
- TASK-15 is done and the owner has deployed the Worker with the four rate limit bindings (search, chat, suggest, data).
- `LIVE_BASE_URL` is set. Run only against the owner's own deployment and from one machine; the test is marked slow (waits for the real window, no fixed sleeps: it polls with `expect.poll` up to a timeout of 2 minutes).
- To avoid cost, the requests go to the cheapest guarded route that does not call the AI service (a data endpoint such as `/api/cities`, or `/search` with empty input as agreed with lead); `/chat` is never hit with valid input.

## Steps
1. Send requests to the chosen endpoint in a loop faster than the configured limit until a 429 is seen (cap at 200 requests).
2. Read the 429 headers and body.
3. Immediately request a different guarded group (for example `/api/suggest?q=ha`).
4. Poll the original endpoint until it returns 200 again.
5. Check the page at `/` still loads during the block.

## Expected results
1. A 429 appears before the cap; earlier requests were 200.
2. The 429 has `Retry-After`, JSON body `{"error":"too_many_requests"}` and the security headers.
3. The other group is not affected (200) because counters are separate.
4. The endpoint returns 200 again within the waiting period (plus a margin of 30 seconds).
5. The ordinary page (no guarded route) is never refused.

## Test data
- Limits from `RATE_LIMITS` (search 20, chat 20, suggest 120, data 60 per minute) unless the owner changed the binding config; the test reads the values from `LIVE_LIMIT_DATA` if set.
