1. Goals and constraints

Goals

  • A bilingual (Vietnamese default, English) directory of hotels with location, images, utilities, rooms, prices and booking rules.
  • The website reads only from D1. It never queries Vectorize or the LLM for directory pages.
  • Prices shown are sheet base price plus a configurable service fee, calculated on the server.
  • Booking rules are shown exactly as written in the Excel sheets.
  • Room details and hotel utilities can be refreshed from mytour.vn, because the sheets may be out of date.

Non-goals

  • Online booking, availability checks and payments (booking is by phone).
  • Copying Mytour prices, booking rules, descriptions, photos or reviews.
  • Replacing the existing chat and RAG features. They stay as deployed.

Targets (proposed, to confirm)

AreaTarget
Directory page time to first byteUnder 300 ms at the edge for cached pages, under 800 ms uncached
Sheet change to site updateWithin one sync cycle (cron interval, for example 1 hour)
Data safetyA failed extraction or crawl never makes a hotel disappear or changes booking rules
AvailabilityPages keep serving the last good data if a sync or crawl fails

5. Database design

Text columns hold the Vietnamese original. A *_search column holds the folded form (lower case, no diacritics, đ as d) because SQLite's diacritic removal does not handle đ. All timestamps are ISO 8601 UTC text. Prices are integer VND.

CREATE TABLE cities (
  slug TEXT PRIMARY KEY,
  name_vi TEXT NOT NULL, name_en TEXT
);

CREATE TABLE hotels (
  id TEXT PRIMARY KEY,                     -- sha256(fileId + ':' + gid), first 16 hex
  slug TEXT NOT NULL UNIQUE,
  city_slug TEXT NOT NULL REFERENCES cities(slug),
  name TEXT NOT NULL,
  name_search TEXT NOT NULL,
  stars INTEGER CHECK (stars BETWEEN 1 AND 5),
  address TEXT, area TEXT, lat REAL, lng REAL,
  description_vi TEXT, description_en TEXT,
  status TEXT NOT NULL DEFAULT 'review' CHECK (status IN ('review','published','hidden')),
  source_file_id TEXT NOT NULL, source_gid TEXT NOT NULL, source_hash TEXT NOT NULL,
  synced_at TEXT NOT NULL,
  rooms_synced_at TEXT, facilities_synced_at TEXT,
  UNIQUE (source_file_id, source_gid)
);
CREATE INDEX idx_hotels_city_status ON hotels (city_slug, status);
CREATE INDEX idx_hotels_status_name ON hotels (status, name_search);

  code TEXT PRIMARY KEY,                   -- e.g. pool, parking, elevator
  category TEXT NOT NULL CHECK (category IN ('facility','service','building','furniture')),

Design notes

  • Hotel id is derived from the Drive file and tab ids, so a rename of a tab does not create a duplicate. The slug is generated once and kept stable.
  • Facilities use a canonical catalogue. A label from the sheet or from Mytour is folded and matched against facility_catalog.synonyms. An unknown label goes to a review list and is not shown until mapped. This keeps both languages consistent and lets filters work.
  • Booking rules are separate so that no crawler code path joins to them.
  • The FTS table is written by the app in the same batch as the hotel row, which keeps it simple and avoids triggers. D1's FTS5 support and its limits should be verified unverified.
  • Status gate: only published hotels are returned by any public query. New hotels start as review, or published automatically when validation passes and the setting auto_publish is on.

6. Sheet sync pipeline

Sequence

cron (hourly)
  scheduled() -> planSync()
      list Drive folder, compare modified time with KV state
      for each changed file: REINDEX_QUEUE <- { type: 'file', fileId, name, ... }
queue consumer
  'file'      -> list tabs, enqueue one 'tab' message per tab, enqueue 'drop-tab' for removed tabs
  'tab'       -> syncTab()
  'drop-tab'  -> hide hotel, delete vectors

syncTab(msg)
  1. fetch tab CSV                                   (existing)
  2. hash = sha256(CHUNKER_VERSION + EXTRACTOR_VERSION + csv)
     if hash == KV hash and not msg.force: stop      (existing pattern)
  3. chunks -> embeddings -> Vectorize upsert         (existing, unchanged)
  4. blocks = splitBlocks(csv)                       (deterministic)
  5. record = parseTables(blocks)                    (rooms, prices, rules rows)
  6. record = await extractFreeText(blocks)          (LLM, schema-checked)
  7. result = validate(record)                       (Zod + business rules)
  8. upsertHotel(result)                             (one D1 batch, step 6.3)
  9. KV put hash and state

Booking rules (hotel and room level)Verbatim text capture of the rules blocks; LLM only fills the optional structured fieldsWording must never change

The parser depends on how your sheets are laid out. This design assumes the sheets keep the layout described earlier (blank rows separate blocks, a lone one-cell block is a heading). Real sample rows are needed to finalise the rules unverified.

6.2 Extraction contract

// Zod schema, shared by the sync and the tests
const ExtractedHotel = z.object({
  stars: z.number().int().min(1).max(5).nullable(),
  address: z.string().max(300).nullable(),
  description_vi: z.string().max(4000).nullable(),
  facilities: z.array(z.string().max(80)).max(80),     // raw labels, mapped to the catalogue later
  furniture: z.array(z.string().max(80)).max(80),
  building: z.object({
    floors: z.number().int().nullable(),
    rooms: z.number().int().nullable(),
    year_built: z.number().int().min(1900).max(2100).nullable(),
  }),
});
// rules: validate(record) rejects the hotel into 'review' when
//  - a room price is present but not a positive integer
//  - an image URL is not https
//  - the same room name appears twice in one tab
//  - description or facilities are missing entirely (warning, not an error)

The LLM call asks for JSON only, with null for anything not stated, and the result is parsed by Zod. A parse failure is retried once, then the hotel goes to review with the reason stored in sync_runs.notes. The model name and prompt version are constants, and EXTRACTOR_VERSION is bumped when they change so tabs are re-extracted.

6.3 Writing to D1

// one batch per hotel: atomic, idempotent
await env.DB.batch([
  upsertHotelStmt,                    // INSERT ... ON CONFLICT(id) DO UPDATE
  deleteChildren('hotel_facilities', id, { source: 'sheet' }),
  ...facilityInserts,
  deleteChildren('hotel_images', id),
  ...imageInserts,
  deleteSheetRooms(id),               // only rooms with source = 'sheet'
  ...roomInserts,
  deleteBookingRules(id),
  ...bookingRuleInserts,
  deleteFts(id), insertFts(id),
  ...applyOverrides(id),
]);
await bumpDataVersion(env.DB);        // invalidates page cache
  • Children are replaced only for rows owned by the sheet. Rows from Mytour (source = 'mytour') are untouched, so a sheet sync does not erase crawled data.
  • Overrides are re-applied at the end of every sync.
  • If D1 batch size or statement limits are reached for large hotels, split into two batches with the hotel row last. unverified

6.4 Failure handling

  • A failing tab is retried by the queue with a delay (as today), then lands in the dead-letter queue.
  • The previous D1 data stays untouched until a new record passes validation.
  • A tab that disappears hides the hotel (status = 'hidden') and deletes its vectors. It is not deleted from D1, so it can be restored.
  • If the Drive folder page returns nothing, the sync throws (existing behaviour) and nothing is removed.

7. Mytour crawl pipeline

This pipeline runs only after the Phase 0 go decision on Mytour's terms and robots.txt. It is disabled by default (crawl_targets.enabled = 0).

7.1 Job lifecycle

weekly cron -> for each enabled target: CRAWL_QUEUE <- { type: 'crawl-start', targetId }

crawl-start    POST https://api.cloudflare.com/client/v4/accounts/{CF_ACCOUNT_ID}/browser-run/crawl
               -> store { id, targetId, status: 'running' } in crawl_jobs
crawl.finished event (Queues event subscription, or a poll with ?limit=1 every few minutes)
               -> CRAWL_QUEUE <- { type: 'crawl-finish', jobId }
crawl-finish   GET .../crawl/{jobId}?status=completed&limit=50&cursor=...   (page until no cursor)
               -> for each record: ingest()
               -> GET ...?status=errored and ?outcome issues: log, disable target on robots/content-signal refusal
               -> mark job finished, target.last_success_at
match-batch    -> match, merge (section 8)
// crawl-start request body (built from the target row)
{
  "url": target.start_url,
  "limit": target.page_limit, "depth": target.depth, "source": "all",
  "render": !!target.render,
  "formats": ["json"],
  "jsonOptions": {
    "prompt": "Extract the hotel name, address, district, star rating, phone, coordinates, the hotel facilities list, and for each room type its name, bed type, size in square metres, maximum guests, view and in-room amenities. Do not extract prices, photos, descriptions, booking policies or reviews.",
    "response_format": { "type": "json_schema", "json_schema": { "name": "hotel", "properties": { ... } } }
  },
  "options": { "includePatterns": [...], "excludePatterns": [...] },
  "crawlPurposes": ["search"], "contentUse": "reference",
  "modifiedSince": lastSuccessUnix, "maxAge": 604800
}
  • The endpoint is asynchronous. A job can run up to 7 days, and Cloudflare keeps results for 14 days, so results are copied into crawl_staging as soon as the job finishes.
  • crawlPurposes and contentUse must be declared truthfully. If the site's Content Signals refuse them, the request is rejected and the target is disabled.
  • Free-plan limits (5 jobs a day, 100 pages a job) make one city per job the maximum useful size. The Paid plan is expected for real use.

7.2 Handling record outcomes

ResultAction
outcome = successValidate with Zod, write to crawl_staging (skip if the hash is unchanged)
robots_disallowed, content_use_disallowed, crawl_purpose_disallowedSet blocked_reason, disable the target, raise an admin alert, never retry automatically
status = errored (for example 403)Count and log. A block is a stop signal, not something to bypass.
timeout, connection_error, browser_unavailableRetry on the next run

8. Matching and merge

8.1 Normalisation

export function fold(s: string): string {
  return s.normalize('NFD').replace(/[̀-ͯ]/g, '')   // strip combining marks
          .replace(/đ/gi, 'd').toLowerCase()
          .replace(/[^a-z0-9\s]/g, ' ').replace(/\s+/g, ' ').trim();
}
const GENERIC = new Set(['khach','san','hotel','resort','spa','and','the']);
export const nameKey = (s: string) => fold(s).split(' ').filter(w => !GENERIC.has(w)).join(' ');

8.2 Hotel match score

candidates = staged Mytour hotels in the same city
for each candidate c of sheet hotel h:
  name   = tokenSetSimilarity(nameKey(h.name), nameKey(c.name))        // 0..1
  addr   = tokenSetSimilarity(fold(h.address), fold(c.address))        // 0..1, 0 if either is empty
  geo    = (distanceMeters(h, c) <= 150) ? 1 : 0                        // only if both have coordinates
  phone  = digits(h.phone) == digits(c.phone) ? 1 : 0                  // only if both have a phone
  stars  = h.stars == c.stars ? 1 : (h.stars && c.stars ? -1 : 0)
  score  = 0.40*name + 0.25*addr + 0.20*geo + 0.05*stars
  if phone == 1 and name >= 0.5: score = max(score, 0.95)
decision:
  best >= HIGH and best - second >= MARGIN  -> status 'auto'
  best >= LOW                               -> review queue
  otherwise                                 -> no match

The weights and thresholds (HIGH, LOW, MARGIN) are starting points. They are chosen by testing on a labelled sample of about 50 hotels, and auto-linking stays off until that is done. If Mytour pages do not show phone or coordinates, those terms drop out and more cases go to review.

8.3 Room mapping

for each Mytour room m of a confirmed hotel:
  candidates = rooms of that hotel with source = 'sheet'
  score = 0.5*tokenSetSimilarity(nameKey(m.name), nameKey(s.name))
        + 0.25*(m.bed_type == s.bed_type)
        + 0.25*(m.max_guests == s.max_guests)
  link when score >= ROOM_HIGH and clearly ahead of the next candidate, else review
unlinked Mytour room -> shown without a price ("Contact for price")
unlinked sheet room  -> kept, flagged for review

Overrides are applied after the merge, so a manual correction always wins. Each changed value writes a field_sources row with the source, URL and fetch time.

9. Pricing service

// src/domain/pricing.ts
export function finalPrice(base: number, feePercent: number): number {
  const pct = Math.min(100, Math.max(0, feePercent));
  return Math.round((base * (100 + pct)) / 100 / 1000) * 1000;   // nearest 1,000 VND
}
// finalPrice(1_250_000, 10) === 1_375_000
  • Source of the percentage: settings.service_fee_percent, read once per request (or cached with the page data version). It defaults to 10. A non-numeric value falls back to 10 and logs a warning.
  • Where it is applied: in the API and page renderers, immediately before output. base_price is never included in any response.
  • Null price: the room shows "Contact for price" (Vietnamese: "Liên hệ"). The headline price is the minimum final price of the hotel's priced rooms, or the same wording if none are priced.
  • Fee note: settings.show_fee_note controls whether "Includes 10% service fee" appears. The percentage in that note comes from the same setting.
  • Disclaimer: the call-to-confirm sentence is rendered by the shared layout next to every price, so no template can omit it. A test checks this.

10. Booking rules

  • Storage: booking_rules.raw_text holds the sheet text exactly as exported. It is HTML-escaped on output and newlines are preserved.
  • Two levels: hotel-level rules (room_id IS NULL) and room-level rules. A room page section shows its own rules first, then the hotel rules.
  • Structured fields are optional extras for filtering and summaries. They stay status = 'review' until an admin confirms them, and only confirmed values are used for filters. The raw text is always the displayed content.
  • Missing rules: render "Please call to confirm" (Vietnamese equivalent), never a default value.
  • Sync date: synced_at is shown next to the rules.
  • Staleness: an admin report lists hotels whose rules text has not changed for a configured number of days, for a person to check.
  • Language: the Vietnamese original is shown on both language versions unless a reviewed translation exists. Translations are stored in a separate column and labelled.
  • Isolation: the crawl and merge code have no write permission to this table (section 8.4).

11.4 Search

// build a safe FTS5 query from user text
const tokens = fold(q).split(' ').filter(Boolean).slice(0, 6);
const match = tokens.map(t => `"${t.replace(/"/g, '')}"*`).join(' AND ');
// SELECT h.* FROM hotels_fts f JOIN hotels h ON h.id = f.hotel_id
//   WHERE hotels_fts MATCH ? AND h.status = 'published' ...

User input is folded and quoted before it reaches the query, so FTS syntax characters cannot be injected. Filters by city, stars and facility are normal SQL conditions with bound parameters.

11.5 Rendering and caching

  • Pages are rendered with Hono JSX components (Layout, HotelCard, RoomRow, PriceBlock, BookingRules, Disclaimer).
  • Pages use the Cache API with a key of URL, language and data_version. Every successful sync or merge increments data_version, which invalidates old entries without explicit purging. Public pages send a short s-maxage and stale-while-revalidate.
  • List queries fetch hotels first, then facilities, images and rooms for those ids in single IN (...) queries, to avoid one query per hotel.
  • Images use loading="lazy", explicit width and height, and the original URLs unless a hotel's consent allows copying to R2.

12. Languages

  • URLs: Vietnamese at / (default), English under /en/. Each page emits <html lang>, hreflang alternates and a canonical link.
  • Dictionary: vi.ts and en.ts export the same typed key set. A unit test fails when a key is missing from either file.
  • Data fields: Vietnamese is the source. English description, labels and translated rules are used when present, otherwise the Vietnamese value is shown. Facility labels come from the catalogue in both languages.
  • Remembering the choice: the toggle writes hd_lang to localStorage inside try/catch. A small script, loaded before the page body, reads it. If the saved value is en and the visitor is on a Vietnamese URL, it redirects to the matching /en/… URL (and back for vi). A first visit with nothing stored stays on Vietnamese.
  • Crawlers and no-JS users are never redirected by script, so each URL has stable content.
// public/lang.js (outline)
try {
  const saved = localStorage.getItem('hd_lang');
  const onEn = location.pathname.startsWith('/en/') || location.pathname === '/en';
  if (saved === 'en' && !onEn) location.replace('/en' + location.pathname + location.search);
  if (saved === 'vi' && onEn)  location.replace(location.pathname.replace(/^\/en/, '') || '/');
} catch (e) { /* storage blocked: stay on the URL's language */ }

14. Operations

Observability

  • Structured JSON logs for every sync step with hotel id, outcome and duration.
  • sync_runs records created, updated and failed counts per run. The admin status page shows the latest run, hotels per status, review-queue size, stale rules and crawl job states.
  • Alerts (email or webhook) for: dead-letter queue messages, a crawl target disabled by a robots or Content Signals refusal, sync not completed in 24 hours, extraction failure rate above a threshold.

Environments and deployment

  • Staging uses its own D1 database, KV namespace and queues, and a copy of the sheets folder or a subset of it.
  • Migrations are SQL files applied with wrangler d1 migrations apply; each is additive and tested on a copy before production.
  • CI (GitHub Actions): install, typecheck, unit and integration tests, wrangler deploy --dry-run; deploy to staging on merge, to production on a manual approval.
  • Rollback: redeploy the previous Worker version; hide a bad hotel by setting status = 'hidden'; restore a field by deleting its override or re-running a forced sync.

Cost and limits to check

Workers AI usage for extraction and crawl JSON, Browser Run and Workers paid-plan limits, D1 row and query limits at your data size, and Queue throughput. None of these has been priced yet unverified.
